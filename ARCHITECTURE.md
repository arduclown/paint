## 1. Общая идея

Приложение разбито на независимые модули. Каждый модуль — отдельный проект
в Solution. Модули общаются друг с другом ТОЛЬКО через интерфейсы,
которые лежат в общем модуле Core.

Почему так: четыре команды работают параллельно. Если модуль A зависит
напрямую от кода модуля B — команда A не может работать, пока B не готов.
Если оба зависят от интерфейса — могут писать код одновременно.

```
Правило номер один: зависимости только через Core.
Ты никогда не пишешь using VectorEditor.Geometry в модуле VectorEditor.IO.
Ты пишешь using VectorEditor.Core.Interfaces и работаешь с IShape.
```

## 2. Технологический стек

| Что | Чем | Почему |
|-----|-----|--------|
| Язык | C# 12 / .NET 8 | Основа всего |
| UI | Avalonia UI 11 | Кроссплатформенность — Windows, macOS, Linux. WPF работает только на Windows |
| MVVM | CommunityToolkit.Mvvm | Атрибуты [ObservableProperty], [RelayCommand] — меньше boilerplate |
| Рендеринг | SkiaSharp (встроен в Avalonia) | Одинаковая отрисовка на всех ОС |
| Матрица | System.Numerics.Matrix3x2 | Трансформации фигур (поворот, масштаб) |
| Сериализация | System.Text.Json | Сохранение/загрузка проекта |
| Тесты | xUnit | Unit-тесты |

### Почему Avalonia, а не WPF

Проект должен работать на трёх ОС. WPF привязан к Windows. Avalonia — это
по сути "WPF для всех платформ". Синтаксис XAML почти идентичен, паттерны те же.

Отличия, которые нужно помнить:
- Файлы разметки имеют расширение `.axaml` (не `.xaml`)
- Пространства имён: `Avalonia.Controls`, `Avalonia.Media` (не `System.Windows.*`)
- Тема оформления: `Avalonia.Themes.Fluent`
- Файловые диалоги: `StorageProvider API` (не `System.Windows.Forms.OpenFileDialog`)
- В остальном — если умеешь WPF, умеешь и Avalonia

## 3. Модули проекта и зависимости

```
GraphicEditor.sln
│
├── src/
│   ├── common/                   ← Общие интерфейсы и типы (Core)
│   ├── TeamCore/                 ← Бэкенд: Document, Undo/Redo, Selection, ViewModels
│   ├── TeamTools/                ← Геометрия: ShapeBase, фигуры, hit-testing
│   ├── TeamImport/               ← Импорт/Экспорт: JSON, SVG, PNG
│   └── TeamUI/                   ← Фронт: AXAML, Views, стили, отрисовка
│
└── tests/                        ← Тесты
```

(Названия папок — как в текущей репе Дениса. Важно не название, а принцип.)

### Граф зависимостей

```
TeamUI (Фронт)
    │
    ▼
TeamCore (Бэкенд + VM) ◄──── TeamImport (Импорт/Экспорт)
    │
    ▼
TeamTools (Геометрия)
    │
    ▼
common (Интерфейсы)  ◄──── все модули зависят от common
```

Что это значит на практике:
- **common** не зависит ни от кого. Это чистые интерфейсы и модели.
- **TeamTools** зависит только от common. Геометрия не знает про UI и сериализацию.
- **TeamCore** зависит от common. Работает с фигурами через IShape.
- **TeamImport** зависит от common. Сериализует IDocument, экспортирует через IShape.
- **TeamUI** зависит от common и TeamCore (байндит View к ViewModel).

## 4. Интерфейсы-контракты

Это самая важная часть. Пока контракты не зафиксированы — никто не может нормально писать код.

Все интерфейсы лежат в `common/Interfaces/`. Вот что есть:

### IShape — фигура (реализует Геометрия, используют все)

Центральный интерфейс. Каждая фигура на канвасе реализует его.

Что в нём:
- `Id` (Guid) — уникальный идентификатор
- `Name` (string) — "Прямоугольник 1" для панели слоёв
- `Position` (Vector2) — позиция центра на канвасе
- `Rotation` (double) — угол поворота в градусах
- `Scale` (Vector2) — масштаб по X и Y. (-1, 1) = отражение по горизонтали
- `TransformMatrix` (Matrix3x2) — вычисляется из Position+Rotation+Scale
- `Style` (ShapeStyle) — цвет обводки, заливки, толщина, прозрачность
- `GetLocalBounds()` — размеры фигуры без учёта трансформации
- `GetWorldBounds()` — габариты на канвасе после трансформации
- `HitTest(point)` — попадает ли точка в фигуру (для клика мышью)
- `Clone()` — глубокая копия (для Copy/Paste и Undo)

### ILayer — слой (реализует Бэкенд, используют все)

Слой хранит упорядоченный список фигур.

Что в нём:
- `Id`, `Name` — идентификатор и имя
- `IsVisible` — виден ли (глаз в панели слоёв)
- `IsLocked` — заблокирован ли (замок)
- `Shapes` — список фигур (порядок = Z-order, 0 = самая нижняя)
- `AddShape/RemoveShape/GetShape` — базовые операции
- `BringForward/SendBackward/BringToFront/SendToBack` — Z-order

### IDocument — документ (реализует Бэкенд, используют все)

Корневой объект. Один документ = один "проект".

Что в нём:
- `Settings` (SceneSettings) — размер холста, цвет фона, сетка
- `Layers` — список слоёв
- `ActiveLayer` — на какой слой добавляются новые фигуры
- `AddLayer/RemoveLayer/MoveLayerUp/MoveLayerDown` — управление слоями
- `FindShape(id)` — найти фигуру по Id во всех слоях
- `GetAllVisibleShapes()` — все фигуры для отрисовки в правильном порядке

### ITool — инструмент (реализует Бэкенд, используют ViewModel-ы)

Паттерн State. Каждый инструмент по-своему реагирует на мышь.

Что в нём:
- `Type` — ToolType (Select, Rectangle, Ellipse...)
- `DisplayName` — "Выделение", "Прямоугольник"
- `OnPointerPressed(point, document, history)` — нажали мышь
- `OnPointerMoved(point, document, history)` — двигаем мышь
- `OnPointerReleased(point, document, history)` — отпустили

### IUndoableCommand / ICommandHistory — Undo/Redo (реализует Бэкенд)

Паттерн Command. Каждое действие = объект с Execute() и Undo().

ICommandHistory — стек команд:
- `Execute(command)` — выполнить и запомнить
- `Undo()` — отменить последнее (Ctrl+Z)
- `Redo()` — повторить (Ctrl+Y)

### ISelection — выделение (реализует Бэкенд)

- `SelectedShapes` — что сейчас выделено
- `Select(shape)` — выделить одну
- `AddToSelection(shape)` — добавить к выделению (Shift+клик)
- `SelectMultiple(shapes)` — выделить рамкой
- `ClearSelection()` — снять выделение
- `SelectionChanged` — событие для обновления UI

### IDocumentSerializer / IExporter / IImporter (реализует Импорт/Экспорт)

- `IDocumentSerializer` — сохранить/загрузить проект (JSON, наш формат)
- `IExporter` — экспорт в SVG или PNG (теряет структуру слоёв)
- `IImporter` — импорт из SVG (парсинг фигур)

### Модели (в common/Models/)

- `ShapeStyle` — цвет обводки (uint ARGB), цвет заливки, толщина, прозрачность
- `SceneSettings` — ширина/высота холста, цвет фона, сетка

## 5. Паттерны проектирования

В проекте три ключевых паттерна. Ниже коротко — зачем каждый.

### MVVM (Model-View-ViewModel)

Разделение данных, логики и UI:
- **Model** — данные: Document, Layer, Shape. Ничего не знает про кнопки и канвас.
- **ViewModel** — логика: что показать, как реагировать на действия пользователя.
- **View** — AXAML: кнопки, панели, канвас. Байндится к ViewModel, не содержит логику.

Зачем: фронт и бэкенд работают независимо. Фронт байндит UI к свойствам ViewModel-а.
Бэкенд меняет свойства ViewModel-а. UI обновляется автоматически.

### Command (Undo/Redo)

Каждое действие — объект с Execute() и Undo(). Стек команд даёт Ctrl+Z/Ctrl+Y.

Зачем: откат без сохранения полного состояния документа после каждого действия.

### State (Инструменты)

Текущий инструмент — это объект, реализующий ITool. Переключение инструмента —
замена объекта. Вместо switch("какой инструмент") вызываем currentTool.OnPointerPressed().

Зачем: добавление нового инструмента — один новый класс, не трогаем существующий код.

## 6. Как устроены фигуры (команда Геометрии)

Все фигуры наследуют от абстрактного `ShapeBase`, который реализует IShape.

```
ShapeBase (abstract)
  ├── RectangleShape   — Width, Height (в локальных координатах)
  ├── EllipseShape     — RadiusX, RadiusY
  ├── LineShape        — StartPoint, EndPoint
  ├── PolygonShape     — List<Vector2> Points
  └── BezierShape      — контрольные точки (если успеем)
```

Ключевая идея: **трансформация — общая, геометрия — своя**.

ShapeBase уже содержит Position, Rotation, Scale и вычисляет матрицу.
Конкретная фигура (например, RectangleShape) только описывает свою
локальную форму: "я прямоугольник 100×50 вокруг центра".

Вся магия поворотов и масштабирования происходит через матрицу — её не нужно
реализовывать отдельно для каждой фигуры.

**HitTest** (попадание точки в фигуру) — алгоритм:
1. Берём мировую точку (координаты клика на канвасе)
2. Применяем обратную матрицу → получаем точку в локальных координатах
3. Проверяем, попадает ли эта точка в простую фигуру (прямоугольник, эллипс и т.д.)

Это работает для любого поворота и масштаба без дополнительного кода.

**Отражение**: Scale = (-1, 1) = отражение по горизонтали, (1, -1) = по вертикали.
Это бесплатно — матрица обрабатывает это автоматически.

## 7. Как устроен документ (команда Бэкенд)

### Иерархия данных

```
Document
  ├── SceneSettings
  │     Width, Height, BackgroundColor, ShowGrid, GridStep
  │
  ├── Layer[0] "Фон"           (IsVisible=true, IsLocked=true)
  │     └── Shapes: [RectangleShape, EllipseShape]
  │
  ├── Layer[1] "Основное"      ← ActiveLayer
  │     └── Shapes: [RectangleShape, LineShape, PolygonShape]
  │
  └── Layer[2] "Верхний"
        └── Shapes: []
```

### Undo/Redo

Каждое действие, которое меняет документ, оборачивается в IUndoableCommand:

```
Пользователь рисует прямоугольник:
  → history.Execute(new AddShapeCommand(activeLayer, newShape))

Нажимает Ctrl+Z:
  → history.Undo()
  → AddShapeCommand.Undo() убирает фигуру со слоя

Нажимает Ctrl+Y:
  → history.Redo()
  → AddShapeCommand.Execute() добавляет фигуру обратно
```

### Выделение

Selection — отдельный объект, не часть Document.
При изменении выделения вызывается SelectionChanged → ViewModel-ы обновляют UI.

## 8. Как устроены ViewModel-ы (Бэкенд + Фронт)

ViewModel-ы — мост между данными и UI. Фронт байндит свои элементы к свойствам ViewModel.

```
MainViewModel (корневая)
  ├── CanvasViewModel      — список видимых фигур, зум, обработка мыши
  ├── ToolbarViewModel     — текущий инструмент, доступные действия
  ├── LayerPanelViewModel  — список слоёв, видимость, блокировка, переключение
  └── PropertyPanelViewModel — свойства выделенной фигуры (цвет, размер, позиция)
```

### Используем CommunityToolkit.Mvvm

```csharp
// Вместо ручного INotifyPropertyChanged:
public partial class ToolbarViewModel : ObservableObject
{
    [ObservableProperty]              // автогенерирует свойство + уведомление
    private ToolType _selectedToolType = ToolType.Select;

    [RelayCommand]                    // автогенерирует ICommand для байндинга
    private void SelectTool(ToolType toolType)
    {
        SelectedToolType = toolType;
    }
}
```

В AXAML:
```xml
<Button Content="□ Rect" 
        Command="{Binding Toolbar.SelectToolCommand}" 
        CommandParameter="1"/>
```

## 9. Как устроен импорт/экспорт

### Внутренний формат (JSON)

Реализация IDocumentSerializer. Сериализует весь Document в JSON и обратно.
Это "сохранение проекта" — сохраняется всё: слои, фигуры, стили, настройки.

Важно: при десериализации нужно создавать правильный тип фигуры по полю "type".
Полиморфная десериализация — через кастомный JsonConverter или фабрику.

### SVG экспорт

Реализация IExporter. Обходит все видимые фигуры документа, для каждой генерирует
SVG-элемент: `<rect>`, `<ellipse>`, `<line>`, `<polygon>`.
Применяет трансформацию через SVG-атрибут `transform`.

### PNG экспорт

Реализация IExporter. Рендерит канвас в растр через SkiaSharp или
Avalonia RenderTargetBitmap. Результат — файл PNG.

### SVG импорт

Реализация IImporter. Парсит SVG (XML), для каждого элемента создаёт
соответствующий IShape и добавляет на активный слой документа.
Достаточно поддержать базовые элементы: rect, ellipse, line, polygon.

### Файловые диалоги

Avalonia StorageProvider API — кроссплатформенный. Не System.Windows.Forms.

## 10. Как устроен UI (команда Фронт)

### Структура окна

```
┌─────────────────────────────────────────────────┐
│                 Тулбар (сверху)                  │
│  [Select] [Rect] [Ellipse] [Line]  |  [Undo] [Redo] [Delete]  |  [Save] [Export]
├──────────┬──────────────────────┬───────────────┤
│          │                      │               │
│  Панель  │                      │    Панель     │
│  слоёв   │       Канвас         │    свойств    │
│  (лево)  │      (центр)         │    (право)    │
│          │                      │               │
│  Слой 3  │   ┌──────────┐       │  Цвет: ■      │
│  Слой 2  │   │  Фигура  │       │  Толщина: 2   │
│  Слой 1  │   └──────────┘       │  X: 100       │
│          │                      │  Y: 200       │
├──────────┴──────────────────────┴───────────────┤
│  Статус: 800×600  |  X: 150  Y: 300  |  Zoom: 100%          │
└─────────────────────────────────────────────────┘
```

### Как связаны View и ViewModel

View (AXAML) байндится к ViewModel, никакой логики в code-behind:

- Канвас байндится к `CanvasViewModel.VisibleShapes` — отрисовывает фигуры
- Тулбар байндится к `ToolbarViewModel.SelectToolCommand` — кнопки инструментов
- Панель слоёв байндится к `LayerPanelViewModel.Layers` — список с видимостью
- Панель свойств байндится к `PropertyPanelViewModel` — редактирование при выделении
- Undo/Redo байндятся к `MainViewModel.UndoCommand/RedoCommand`

### Канвас

Фигуры на канвасе можно отрисовывать двумя способами:
1. **ItemsControl с Canvas** — каждая фигура = элемент в коллекции. Проще, но менее гибко.
2. **Кастомный Control с DrawingContext** — ручная отрисовка. Быстрее, полный контроль.

Для начала подойдёт первый вариант. Если будет тормозить — переделать на второй.

### Маркеры выделения

Когда фигура выделена — вокруг неё 8 маркеров масштабирования (по углам и серединам)
и 1 маркер поворота (сверху). Это отдельный визуальный слой поверх фигур.

## 11. Соглашения

### Код
- Nullable включён (`<Nullable>enable</Nullable>`)
- PascalCase для классов и методов, camelCase для переменных
- Интерфейсы начинаются с `I` (IShape, ILayer)
- XML-документация (`///`) на публичных классах и методах
- Никакой логики в code-behind AXAML — только через ViewModel
- Не использовать `System.Windows.*` — только `Avalonia.*`

### Git
- `master` — стабильный код
- `develop` (или feature-ветки от master) — текущая разработка
- Ветки на задачу: `feature/rectangle-tool`, `feature/svg-export`
- Перед пушем: `dotnet build` (собирается) + `dotnet test` (тесты проходят)

### Файловые пути
- Использовать `Path.Combine()`, не хардкодить разделители
- Это кроссплатформенный проект — `/` на Linux, `\` на Windows

## 12. Что делать если нужно поменять контракт

Контракты в common — это договорённость между командами. Менять их можно,
но по процедуре:

1. Сформулировать что хочешь поменять и зачем
2. Написать в общий чат — чтобы все команды увидели
3. Убедиться что это не ломает другие команды
4. Внести изменение в common, запушить
5. Все подтягивают обновлённый common

Примеры нормальных изменений:
- "Нужен метод GetPath() в IShape для SVG-экспорта" — ок, обсуждаем и добавляем
- "Хочу поменять uint на Color в ShapeStyle" — нет, Color это UI-тип, Core не должен от него зависеть
